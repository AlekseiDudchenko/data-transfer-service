Scaling Large Data Transfers

Large data-transfer systems are easier to reason about when pull-based and push-based models are kept separate. They solve different operational problems and introduce different failure modes. Some concerns—such as idempotency, checkpointing, consistency, and observability—apply to both.

Two Different Transfer Models

A common source of confusion is to describe pull-style iteration, backpressure through synchronous reads, Kafka-style delivery, and queue-based buffering as one linear evolution. They are not one model.

Pull-based transfer

The consumer controls when the next record or batch is requested.

Iterator Database cursor Pagination HTTP client Batch reader
TransferService ↓ request next item / batch Source ↓ Target

Typical characteristic: natural flow control. If the target is slow, the consumer simply requests the next item later.

Push-based transfer

The producer emits data independently and consumers must keep up or buffer it.

Kafka RabbitMQ Event streams CDC Async workers
Producer ↓ publish Queue / Stream ↓ Consumers ↓ Target

Typical characteristic: decoupling and buffering. If consumers are slower, lag or queue depth increases.

Pull-based Evolution

This path fits database migrations, API imports, file readers, and connector-style transfer services where the consumer actively requests data.

1

Sequential transfer

Read one record and write one record.

Simple and easy to reason about.

Limitation: poor throughput or excessive memory if everything is preloaded.
2

Lazy reading

The dataset is too large to materialize.

Use cursor, iterator, streaming, or pagination.

New concern: resource lifetime and cursor/connection cleanup.
3

Batch writes

Per-record writes cause too many round trips.

Accumulate records and write in batches.

New concern: partial batch failure and transaction boundaries.
4

Retry

Transient failures should not abort long transfers.

Retry with exponential backoff and jitter.

New concern: duplicates if a write succeeded but acknowledgement was lost.
5

Idempotency

Retries can repeat writes.

Use UPSERT, unique keys, or idempotency keys.

Now retries are safer, but restart still begins from zero unless progress is persisted.
6

Checkpointing

Restarting after millions of records is expensive.

Persist last processed ID, page token, or source cursor state.

New concern: consistency between successful target writes and checkpoint updates.
7

Parallel pull

One consumer is too slow.

Partition the keyspace and let multiple workers pull independent ranges.

New concern: ordering, skew, source load, target contention, connection pool limits.
8

Bulk path

Per-record application processing becomes the bottleneck.

Use COPY, Parquet, CSV, object storage, native import/export.

Trade-off: less flexibility for record-level logic.

Push-based Evolution

This path fits event-driven systems, CDC pipelines, durable streams, and continuously running integrations where producers emit data independently.

1

Direct push

Producer sends directly to consumer or target.

Low latency and simple topology.

Limitation: tight coupling; producer is affected by consumer outages.
2

Durable queue or stream

Producer and consumer need decoupling.

Introduce Kafka, RabbitMQ, or another durable broker.

New concern: offsets, lag, redelivery, retention, and broker operations.
3

Consumer retries

Individual messages may fail temporarily.

Retry with backoff; optionally delay or requeue.

New concern: poison messages and endless retry loops.
4

DLQ / failure isolation

One bad record should not block the whole stream forever.

Send permanently failing messages to a dead-letter queue.

New concern: replay, audit, and operational handling of failed messages.
5

Idempotent consumers

At-least-once delivery may redeliver messages.

Make consumer writes idempotent.

This is usually simpler than trying to guarantee global exactly-once semantics.
6

Scale-out consumers

One consumer cannot keep up.

Use consumer groups and partitioned processing.

New concern: partition ordering, rebalance, hot partitions, uneven load.
7

Backpressure / flow control

Producers can outpace consumers.

Bound queues, pause consumption, limit in-flight work, or rely on broker retention.

Unlike simple pull, lag becomes a first-class operational metric.
8

Replay and recovery

Consumers may need to rebuild state.

Replay from offsets or retained log history.

New concern: schema evolution and compatibility across historical messages.

Shared Concerns Across Both Models

Idempotency

Required whenever the same logical record may be processed more than once.

Consistency

Define whether the transfer reads a snapshot, a live source, or a change stream.

Checkpointing

Pull systems persist source position; push systems persist offsets or acknowledgements.

Ordering

Parallelism and partitioning may change global or per-key ordering guarantees.

Observability

Track throughput, failures, retries, lag, progress, and completion status.

Reconciliation

Verify that source and target agree after transfer or after a replay window.

Practical rule:
Do not treat queue-based event processing as the final stage of every data-transfer architecture. Pull and push are different operating models. Choose the model first, then evolve reliability, throughput, recovery, and observability within that model.
